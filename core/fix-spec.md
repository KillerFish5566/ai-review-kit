# 審查修正規範（review-fix 的做法）

> 開發 AI 拿到獨立審查報告後照本檔處理。範本在 `templates/fix.md`。
> 原則：**每一項都要有交代**，不能刪、不能跳過、不能自己宣告通過。

## 1. 步驟

1. 讀審查報告 `.ai-review/reviews/R-xxx.md`（使用者指定的，或最新的一份）。
2. 逐項處理，每一項只能是下列四種結果之一：

| 結果 | 條件 | 要留下的證據 |
|---|---|---|
| `fixed` | 已修正並做了**針對性驗證** | 改了哪個檔案哪幾行；驗證命令與輸出（新增的測試、手動重現步驟） |
| `disputed` | 你認為發現不成立 | 理由要能被第三方檢驗：貼程式碼路徑、說明為什麼不會發生。**不能只寫「不會有這個問題」** |
| `deferred` | 成立但這次不修（使用者決定） | 使用者同意的紀錄、列入 `config.md` 第 6 節未驗證事項 |
| `needs-info` | 資訊不足無法判斷 | 你需要什麼、問誰 |

3. 阻擋級（critical／high）的發現不得 `deferred`，除非使用者明確拍板並記錄。
4. 「待驗證」的疑點也要逐項回應（確認成立→修；確認不成立→disputed 附理由）。
5. 針對性驗證：修什麼就驗什麼。修注入就用惡意輸入實測；修權限就用另一個角色實測。跑不了就寫「未能驗證＋原因」。
6. 全部處理完：
   - 寫 `.ai-review/fixes/F-xxx.md`（`review` 欄填 R-xxx）。
   - 重新照 `handoff-spec.md` 交接：`snapshot` → `checks --run` → 新的 `H-yyy.md`，檔頭 `recheck_of: R-xxx`。修正報告的 `handoff` 欄填 H-yyy。
   - `kit.py state` 應顯示「待複查」。
7. 告訴使用者：處理了幾項、幾項修了、幾項不成立（理由一句）、幾項要他決定，下一步是再讓 Codex 審一次。

## 2. 不可以

- 不可以把狀態改成 `no-blocking-found`，那是審查 AI 的事。
- 不可以在修正時順手改無關的東西（會擴大複查範圍）；真要改，另開一次交接。
- 不可以移除或放寬審查者指出的既有安全機制來「解決」發現。
