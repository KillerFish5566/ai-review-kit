# 交接規範（review-ready 的產物）

> 開發 AI 完成一個完整、可獨立理解的變更後，照本檔產生交接報告。範本在 `templates/handoff.md`。
> 目的：讓審查 AI 與使用者不用問「你到底改了什麼、跑過什麼」，也讓狀態能綁在明確版本上。

## 1. 什麼時候做

- 一個變更**做完了**：功能可用、你自己認為可以送審。不是每次回覆都做。
- 一個變更＝一個能獨立理解的單位（一個功能、一個修正、一次重構）。太大就拆，太小就等累積。
- 修正審查發現後也要重新交接（`recheck_of` 填審查編號）。

## 2. 步驟（照順序，不跳）

1. **確認範圍**：一句話說這次變更是什麼、不含什麼。
2. **釘版本**：`py -3 .ai-review/kit/kit.py snapshot --json`
   - 得到 `id`（H-日期-時間）、`target`（指紋）、`snapshot_ref`、`head`、`base`、工作目錄狀態（修改／未追蹤數）。
   - 未提交與未追蹤的檔案**會被納入指紋與快照**，不會靜默排除。如果裡面有不該送審的東西（暫存檔、實驗碼），先處理掉再重跑 snapshot。
   - 基準（base）：預設 `config.md` 的 `base_ref`；分支上開發就是與主幹的分岔點；找不到就用上一份交接的快照參照。報告裡寫清楚用的是哪個。
3. **跑檢查**：`py -3 .ai-review/kit/kit.py checks --run --handoff <id>`
   - 逐條執行 `config.md` 第 4 節的檢查命令，結果寫進 `.ai-review/.cache/checks-<id>.json` 並印出 Markdown 表。
   - 每條只有四種結果：`pass`／`fail`／`skipped`（環境不足或命令不存在）／`not-run`。**沒跑就是沒跑，不能寫 pass。**
   - 必要（required）檢查 fail 或 skipped 時，交接照做，但狀態摘要要寫「有必要檢查未通過」，並列在「已知風險」。
4. **重大變更的設計檢查**：如果這次動到登入、權限、敏感資料、對外介面，先照 `security-checklist.md` 第 2 節做設計層檢查，把結論寫進第 6 節。
5. **寫交接報告**：複製 `templates/handoff.md` 到 `.ai-review/handoffs/<id>.md`，填滿每一節。
6. **推導狀態**：`py -3 .ai-review/kit/kit.py state`，確認顯示「待獨立審查」（或「待複查」）。
7. **告訴使用者**（三到五句白話）：改了什麼、檢查結果、有什麼風險、下一步是開 Codex 審查。

## 3. 報告必填內容

| 節 | 內容 | 為什麼 |
|---|---|---|
| 檔頭 | `id`、`created`、`target`、`snapshot_ref`、`head`、`base`、`recheck_of`、`scope` | 狀態推導與版本綁定靠這幾個欄位 |
| 1 變更摘要 | 非技術使用者看得懂的三句話 | 使用者要能決定「要不要送審」 |
| 2 變更範圍 | 動到的檔案清單（`git diff --stat <base>..<snapshot_ref>`）、新增／刪除的依賴、設定變更 | 審查 AI 決定要讀哪些完整檔案 |
| 3 重要相關檔案 | 沒改但審查必看的檔案（被呼叫的、設定、權限判斷所在） | diff 看不出上下文 |
| 4 工作目錄狀態 | 分支、HEAD、是否乾淨、未追蹤檔案數、快照參照 | 追溯 |
| 5 檢查結果 | `checks --run` 的表：命令、結果、耗時、輸出尾段、適用的工具版本 | 「跑過什麼」要有證據 |
| 6 設計檢查 | 有動到高風險面向時的結論；沒有就寫「不適用：本次未動到」 | 早期攔截 |
| 7 已知風險與未驗證 | 沒跑的檢查、沒測的情境、你不確定的地方 | 審查 AI 從這裡優先看 |
| 8 給審查者的提示 | 你建議先看哪裡、你最沒把握的是什麼 | 縮短審查時間 |
| 9 自查聲明 | 固定一句：「本報告為開發 AI 自查，不是獨立審查。」 | 防止被當成通過 |

## 4. 不可以

- 不可以把「我看過了」寫成「已測試」。
- 不可以省略未追蹤檔案；不確定要不要納入就問使用者，或先移到專案外。
- 不可以自己把狀態改成 `no-blocking-found`。
- 不可以在交接後再改程式碼卻不重新交接（hook 會提醒，但責任在流程）。
